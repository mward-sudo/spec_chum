# Large-module responsibility map (#446)

This map identifies responsibility boundaries in three large Rust modules. File size is a review signal, not an extraction goal. Keep public APIs stable and extract one cohesive responsibility per change; emulator timing and behavior remain the authority for `machine` changes.

## `host_api` boundary (#445)

`host_api` is the stable runtime/session facade shared by first-party hosts and agent tools. Its core contract is `HostSession`: create/select/reset a machine; load and control media; advance/render frames and read status/audio; deliver input; and inspect/control the debugger. These operations belong together because they act on the same live `Machine` and its observable state. The C ABI in `ffi` adapts that contract for Swift; it is an adapter, not a second owner of emulator behavior.

The callers confirm this boundary: `app`, `windows_shell`, `linux_shell`, the macOS FFI bridge and `living_room` need a live session; `control_plane` and `debug_cli` expose the same session to automation. Keep those paths backed by one `HostSession` source of truth. In particular, do not move model/media/debug operations into individual shells or duplicate machine state in `control_plane`. The dependency direction supports the same shape: `host_api` depends on `machine`, `formats` and host utility/concurrency crates; shells, `living_room` and `control_plane` depend on `host_api`, with no UI or agent dependency flowing back into it.

| Responsibility | Current owner | Caller evidence | Boundary assessment |
| --- | --- | --- | --- |
| Live machine lifecycle, media control, input, frame/audio/status and debugger access | `session.rs` (`HostSession`) | All four hosts plus `control_plane` / `debug_cli` use the session; `ffi` forwards to it. | Stable host/session API. Keep shared operations here or in cohesive private helpers used by it. |
| FFI handles and `sc_*` C ABI | `handle.rs`, `ffi/` | `apps/macos` calls the C header; `living_room` embeds the same library. | Host-language adapter. It should delegate to the safe session API; it is not an independent service owner. |
| On-disk UI preferences, recent files, window/audio/input choices and model profile records | `prefs.rs` | egui, Win32, GTK4 and `living_room` load or update the common preferences; macOS mirrors the documented fields in `UserDefaults`. | Ancillary host configuration, not live emulator state. It is already a distinct module and schema. Its cross-host reuse is a concrete reason to keep the shared implementation available; a separate crate has no demonstrated caller need yet. |
| User ROM paths and ROM setup payload/install helpers | `rom_setup.rs` | egui, Win32, GTK4 and macOS setup flows read/update these; the C ABI synchronizes macOS paths. `machine` remains the authority for ROM requirements and availability. | Ancillary machine-setup service. Keep path/UI setup out of `HostSession`; retain calls into `machine` rather than duplicating ROM policy. Existing module boundary is sufficient. |
| User machine-profile schema and validation | `machine_config.rs` | Preference records and host setup flows share configuration validation; construction ultimately feeds the session/machine path. | Ancillary configuration model, distinct from a running machine. Keep validation/source-of-truth shared; no separate crate is justified by current callers. |
| Key mapping | `keymap.rs` | Native/egui input adapters use host-facing key codes; macOS maintains a parity mapping. | Input adapter utility, not session state. Keep mapping at the host boundary and avoid embedding platform key policy in `machine`. |
| Tape identity and optional online title enrichment | `session.rs` identity/state plus `media_title_lookup.rs` lookup/cache helpers | `HostSession::open_tape` owns the loaded-media identity and applies lookup results; network lookup is opt-in (`online_tape_titles`, default off). | Ancillary metadata service with session-scoped coordination. The lookup/cache logic already has its own module; identity, opt-in choice and stale-result handling belong with the loaded session. No caller evidence supports moving it out of `host_api` or splitting it into a crate. |

**Conclusion:** the crate name currently hides several responsibilities, but source and callers show a useful distinction rather than a justified crate split. Preserve `HostSession` as the stable cross-host runtime API and treat preferences, ROM setup, machine profiles, key mapping and title lookup as ancillary host services with their existing module seams. Revisit ownership if a concrete non-host caller needs one service independently, or if a new host cannot consume the current shared API without pulling unrelated behavior. This map proposes no code movement.

## Ranked extraction candidates

Ranks indicate a useful first extraction to investigate, not a commitment to split every candidate.

1. **Host tape identity/enrichment** (`host_api/src/session.rs`, approximately lines 321–460). The identity setters, source/hash accessors, opt-in online lookup and pending-result application form a distinct media-metadata responsibility. Risk: it shares `HostSession` fields and must preserve opt-in privacy, generation checks against stale async results, and clearing on media/model changes. Validation: focused `host_api` tests for local identity, opt-in lookup, stale-result rejection and clearing; `./scripts/check_crates.sh host_api`.
2. **App ROM setup and custom configuration dialogs** (`app/src/lib.rs`, approximately lines 1349–1869). These are presentation flows around ROM availability and user machine profiles, separate from frame UI and debugger rendering. Risk: dialog actions mutate shared session/preferences and trigger persistence or machine rebuilds. Validation: existing app/config tests plus focused UI tests for save/cancel/error paths; `./scripts/check_crates.sh app`.
3. **Machine model metadata/construction** (`machine/src/lib.rs`, approximately lines 402–461 and 906–1104). Model classification and constructor selection are conceptually distinct from execution. Risk: constructor setup encodes bus/ULA/model invariants, ROM validation and special-model differences. Validation: run the focused model-construction tests and `./scripts/check_crates.sh machine`; preserve existing timing and model assertions.
4. **Machine frame/tape execution** (`machine/src/lib.rs`, approximately lines 1992–3095). Frame advancement, tape EAR/traps and convenience loading are a possible future boundary only after mapping their shared invariants. Risk: highest; helpers interact with CPU registers, bus paging, tape state, ULA/frame time and intentionally distinct convenience versus hardware timing. Validation must include the existing timing/tape tests and machine crate gate; do not extract merely to reduce line count.

No extraction is performed by this map. For each follow-on, select one candidate, keep the public API stable, and compare behavior through focused tests before considering another boundary.
